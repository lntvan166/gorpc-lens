# gorpc-lens — Design

Date: 2026-09-10
Status: Approved, ready for implementation planning

## Problem

In a Go microservice repo, Ctrl+Click on a gRPC client call lands on generated
code instead of the handler that actually runs.

Concretely, in the reference workspace:

- `order-biz/manager/biz/order.go:94` calls
  `b.orderClient.ListOrders(...)`, where `orderClient` is typed
  `pbOrder.OrderServiceClient`.
- The code that runs is
  `order-svc/manager/handler/order.go:47`, a method on
  `*OrderHandler`, registered by
  `pbOrder.RegisterOrderServiceServer(server, orderHandler)` in
  `order-svc/main.go:29`.
- Ctrl+Click goes to
  `protos/order-svc/order_service_grpc.pb.go:79` — the
  `OrderServiceClient` interface declaration.

This is not a gopls defect and no gopls setting fixes it.
`XxxServiceClient` and `XxxServiceServer` are two unrelated interfaces with no
type-level edge between them. "Go to Implementation" on the client method
returns the generated private `xxxServiceClient` struct, never the handler. The
only thing connecting caller to handler is the gRPC service and method name.

gorpc-lens bridges that gap.

## Key insight

The extension does not need to understand Go.

Files generated by `protoc-gen-go-grpc` are rigidly formatted, and within one
file `XxxServiceClient` and `XxxServiceServer` always carry identical method
sets. So the extension parses exactly one file — the generated `_grpc.pb.go`
it has been pointed at — to hop from a client interface method to its server
counterpart, and hands that position to gopls. gopls does every piece of real
work: resolving the receiver's type, import aliases, cross-module search.

Nothing about the consuming repo is encoded anywhere: not the `pbOrder`
alias, not the `example.com/org/...` module paths, not the
`manager/handler/` convention. That is why the extension is generic across Go
gRPC repos at no extra cost.

## Verified assumptions

Measured against the real reference workspace (~50 modules under one `go.work`,
gopls v0.23.0). All times are cold CLI start, which loads the entire workspace
from nothing; they say nothing about warm in-editor latency.

| Query | Input | Result | Cold |
|---|---|---|---|
| `implementation` | `order_service_grpc.pb.go:674:2` (server iface method) | `order-svc/manager/handler/order.go:47:30` | 6.7s |
| `implementation` | `order-svc/manager/handler/order.go:47:30` (handler method) | `order_service_grpc.pb.go:674:2` | 3.1s |
| `references` | `order_service_grpc.pb.go:79:2` (client iface method) | 20+ call sites across `billing-svc`, `integration-svc`, `invoice-biz`, `mobile-biz` | 6.0s |

Established by this:

1. gopls resolves implementations across module boundaries inside a `go.work`.
2. The implementation relation is bidirectional — handler to interface method
   works as well as interface method to handler.
3. References on the client interface method finds real cross-service callers.
4. The generated header carries `// source: order-svc/order_service.proto`,
   so locating the `.proto` needs no proto parsing.

Not established, and the first thing implementation must measure: **warm
in-editor latency of an `implementation` query on a 50-module workspace.**

## Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Generality | Generic, conventions configurable | Resolution keys off `protoc-gen-go-grpc` output shapes, which are standard everywhere. repo-specific layout is never encoded. |
| Engine | Delegate to gopls; no index | Always type-accurate, roughly 400 lines, no watcher or invalidation logic. A ripgrep index is 4x the code for a worse answer. |
| Navigations in v1 | Call to handler; handler to callers; either side to `.proto` | |
| Explicitly excluded | Handler to downstream biz | `h.orderBiz.ListOrders` is a concrete struct in the same module; gopls already handles it. |
| Workspace shape | Single root containing all modules | The the monorepo root folder is opened whole. `go.work` is inside it. |

Rejected: an own ripgrep/regex index (fragile against multi-line signatures,
streaming RPCs, embedded `Unimplemented`, import aliases; needs a file watcher
and cache invalidation). Rejected: a hybrid index-plus-gopls design — revisit
only if measured warm latency proves approach A too slow.

## Architecture

A vscode-free core plus a thin VS Code adapter layer. Exactly one module
knows anything about Go syntax. The core takes plain paths and positions so it
is unit-testable outside the extension host; the adapter translates to and from
the VS Code API.

### `pbFile.ts`

The only Go parsing in the extension. Given a `*_grpc.pb.go` document, produce:

```
{
  protoSource: string,            // from the `// source:` header comment
  services: [{
    name,                         // e.g. "OrderService"
    clientInterface: { name, methods: Map<string, Position> },
    serverInterface: { name, methods: Map<string, Position> },
  }],
}
```

Implemented as a line scanner with brace-depth tracking — locate
`type X interface {`, collect `Name(` at depth 1, close on the matching brace.
Not a regex pile. Safe because the input is generated code with a fixed shape.

Cached per `document.version`.

### `locator.ts`

Given a URI and position, classify it: inside a client interface method
declaration, inside a server interface method declaration, or neither. Returns
`{ service, method, clientPos, serverPos }`.

### `resolver.ts`

Wraps `vscode.executeImplementationProvider` and
`vscode.executeReferenceProvider`, then filters results (see Filtering).

## Core flow

Ctrl+Click at `order-biz/manager/biz/order.go:94` on `ListOrders`:

1. **Cheap reject.** Not a Go file, token not capitalized, or not followed by
   `(` — return immediately. Keeps the extension out of the way for the
   overwhelming majority of clicks.
2. **Reentrancy guard**, keyed on `uri#position`. Step 3 calls back into this
   provider; the guard returns null on reentry.
3. **`executeDefinitionProvider`** at the position → `order_service_grpc.pb.go:79`.
4. **Classify** via `pbFile.ts`. Inside a `*ServiceClient` interface in a
   `_grpc.pb.go`? Yes → `OrderService.ListOrders`.
5. **Sibling lookup** → `OrderServiceServer.ListOrders` at pb.go:674.
6. **`executeImplementationProvider`** at pb.go:674 → `handler/order.go:47`.
7. **Return** as `LocationLink[]`.

VS Code merges this with gopls's own result, so Ctrl+Click opens a peek list
holding both the generated interface and the real handler.

The reverse flow is symmetric: from a handler method,
`executeImplementationProvider` gives the server interface method, the sibling
lookup gives the client interface method, and `executeReferenceProvider` gives
the callers.

## User-facing surfaces

**Definition provider** augments Ctrl+Click, per the core flow. Fires at a call
site in a caller service and on the client interface method inside the pb.go.

**Reference provider** augments Shift+F12 on a handler method, contributing
cross-service call sites into the normal references panel alongside gopls's
in-module results.

**Commands** — Command Palette plus an editor context submenu gated on
`editorLangId == go`. Each works from either end: a call site, a handler
method, or inside the pb.go.

| Command | Binding | Behavior |
|---|---|---|
| `gorpc-lens: Go to gRPC Handler` | `Ctrl+Alt+H` | Direct jump when there is one handler, peek when several. |
| `gorpc-lens: Find gRPC Callers` | unbound | Reverse direction via `editor.action.showReferences`. |
| `gorpc-lens: Go to Proto Definition` | unbound | Read `// source:` from the pb.go header, `findFiles` on that path suffix, locate `rpc <Method>`. |

The handler command exists because gopls always contributes the interface, so
Ctrl+Click will always open a peek list. Daily use wants a direct landing.
Only that one ships bound, to avoid squatting on the user's keymap.

**CodeLens**, off by default (`gorpcLens.codeLens.handlers: false`). When on, a
`N callers in M services` lens above each handler method, resolved lazily so
only visible lenses cost a query. Default off because handler files carry ~30
methods and each lens is a workspace-wide references query.

## Filtering

What counts as a real result, all overridable by setting:

- Drop anything matching `excludeGlobs` (default `**/*.pb.go`) — the
  `_Xxx_Handler` trampolines and the private `xxxServiceClient` struct.
- Drop receivers named `Unimplemented*` or `Unsafe*`.
- Drop `*_test.go` unless `gorpcLens.includeTests` is true — mocks and fakes
  otherwise crowd the picker.

## Performance

Each gRPC Ctrl+Click costs two sequential gopls round trips. The first is
cheaper than it appears: VS Code is already asking gopls for the definition at
that exact position, so the duplicate query hits a warm cache. The second — an
`implementation` query across 50 modules — is the unknown.

**Implementation starts with a measurement task, not code.** Instrument the
pipeline, run it in the real the monorepo root workspace, record p50/p95 for warm
implementation queries. Under roughly 500ms p95, approach A is settled and the
hybrid is never built. If it is seconds, revisit with numbers.

Three mitigations regardless:

- **Cheap rejects** before any LSP call.
- **Cache** keyed `service/method/direction`, holding resolved locations,
  invalidated wholesale on any `.go` save. Crude, but saves are rare next to
  clicks and a stale jump target is worse than a re-query.
- **Hard timeout** `gorpcLens.timeoutMs` (default 2000) via `Promise.race`. On
  timeout, return nothing; Ctrl+Click behaves as it does today. The editor
  never hangs on the extension.

## Failure handling

One principle: every failure path returns no extra results. The worst outcome
gorpc-lens can produce is the behavior the user has today.

The asymmetry that matters:

- **Providers fail silently.** The user asked VS Code, not us.
- **Commands fail loudly** — "No handler found for
  `OrderService/ListOrders`", "Go language server not ready". The user
  did ask us, and silence there is just a broken keybinding.

Because the failures are invisible by design, the extension needs a debugging
story: an output channel logging each pipeline stage and its timing under
`gorpcLens.trace: verbose`. Without it, "Ctrl+Click didn't offer the handler"
is unfalsifiable.

## Configuration

| Setting | Default | Purpose |
|---|---|---|
| `gorpcLens.enabled` | `true` | Master switch. |
| `gorpcLens.timeoutMs` | `2000` | Per-query gopls timeout. |
| `gorpcLens.includeTests` | `false` | Include `*_test.go` results. |
| `gorpcLens.codeLens.handlers` | `false` | Caller-count lens above handler methods. |
| `gorpcLens.excludeGlobs` | `["**/*.pb.go"]` | Generated-file filter; configurable for non-standard generators. |
| `gorpcLens.trace` | `"off"` | `off` or `verbose`. |

## Testing

TDD, in this order:

1. **`pbFile.ts` parser** — pure functions, no VS Code, fast. This is where the
   bugs live. Fixtures: a copy of the real
   `order_service_grpc.pb.go`; a service with streaming RPCs; a service
   with multi-paragraph doc comments between methods (reference-workspace has these, and a
   naive scanner breaks on them); a service with zero methods.
2. **Result filters** — table-driven over synthetic location lists covering
   generated trampolines, `Unimplemented*` embeds, and test mocks.
3. **Integration** via `@vscode/test-electron` against a fixture Go workspace
   committed to the repo — two tiny modules, a `go.work`, one real generated
   pb.go — asserting the definition provider returns the handler. This is the
   only test that catches a break in the gopls contract. It needs Go and gopls
   available in CI.

## Packaging

TypeScript, esbuild bundle, zero runtime dependencies — everything is the
VS Code API. `activationEvents: onLanguage:go`. Local `.vsix` install for a private monorepo;
Marketplace publishing deferred, and nothing in the design blocks it.

## Scope boundary for v1

Not in v1, stated so the implementation plan cannot drift into it:

- No gRPC reflection.
- No running-server discovery.
- No service-to-repo configuration file.
- No proto compilation.
- No handler-to-biz hop (gopls already covers it).
- No multi-root or cross-window workspace support beyond what a single root
  gives for free.
